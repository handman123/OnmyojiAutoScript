# 排队模式 — 需求文档

## 1. 背景与问题

### 1.1 现状

本脚本支持同时运行多个实例，每个实例通过独立的多进程（`multiprocessing.Process`）控制一台模拟器。每个实例内部运行一个无限循环的任务调度器（`Script.loop()`），按配置文件中的时间表周期性执行游戏任务。

### 1.2 核心问题

任务具有周期性，一天中大部分时间处于待机状态（idle），仅少数时间点会触发任务执行。当同时控制 5~6 个模拟器时，会出现以下问题：

```
时间轴：  ──────────────────────────────────────────────────────→

实例 A：  [待机···········] [████任务████] [待机············]
实例 B：  [待机···········] [████任务████] [待机············]
实例 C：  [待机···········] [████任务████] [待机············]
实例 D：  [待机···········] [████任务████] [待机············]
实例 E：  [待机···········] [████任务████] [待机············]

          同一时间点（如服务器刷新 09:00），所有模拟器同时启动任务
          → CPU/内存/磁盘 IO 瞬时飙升 → 服务器压力巨大
```

每个任务执行时涉及：
- ADB 截图（高频 I/O）
- OCR 识别（CPU 密集）
- 模板匹配/图像识别（CPU 密集）
- 模拟触控操作
- 日志写入磁盘

**5~6 个实例同时执行任务时，这些操作同时发生，造成资源争抢，甚至可能导致部分任务因超时失败。**

### 1.3 典型场景

- 每天 09:00或17:00 服务器刷新，多个账号同时触发"逢魔之时"、"地域鬼王"等日常任务
- 每天 12:00/18:00/20:00 的限时活动
- 用户手动触发多个实例同时执行同一任务

## 2. 功能概述

在脚本配置中新增一个选项：**"是否开启排队模式"**。

当多个配置（实例）都勾选了此选项时，它们将**排队依次执行任务**，而非并行执行。具体规则：

> 当前持有"执行权"的实例必须完成其**当前时间节点的所有待执行任务**，且确认**未来 10 分钟内没有任何任务**，才释放执行权给队列中的下一个实例。

## 3. 详细需求

### 3.1 配置项定义

| 字段 | 说明 |
|------|------|
| 所属位置 | Script 根级配置（与 `when_task_queue_empty`、`schedule_rule` 同级） |
| 配置名称 | `queue_mode` |
| 中文名 | 排队模式 |
| 类型 | `bool` |
| 默认值 | `False`（关闭，保持现有行为不变） |
| 附加参数 | `queue_idle_threshold`：释放执行权的空闲阈值，类型 `int`，单位分钟，默认 `10` |

### 3.2 排队规则

#### 3.2.1 执行权的获取

- 实例在 `get_next_task()` 判定某个 `task.next_run <= now`（任务到期，准备执行）时，**在实际执行前**尝试获取执行权
- 如果当前没有实例持有执行权，该实例**立即**获得执行权并开始执行
- 如果执行权已被其他实例持有，该实例进入**等待队列**，每 5 秒轮询一次直到获得执行权
- 等待队列采用**先到先得（FCFS）** 的规则

#### 3.2.2 执行权的持有

- 持有执行权的实例可以连续执行所有 `pending_task` 中的任务
- 每执行完一个任务后，重新评估是否应该释放执行权

#### 3.2.3 执行权的释放

满足以下**两个条件**时释放执行权：

1. **当前时间节点任务全部完成**：`pending_task` 为空（即所有已启用的任务，其 `next_run` 都在未来）
2. **未来 10 分钟内无任务**：`waiting_task` 中最早的任务的 `next_run` 距离当前时间 > 10 分钟（`queue_idle_threshold` 可配置）

如果条件 1 满足但条件 2 不满足（即 10 分钟内还有任务），实例**继续持有执行权并等待**，待该任务到期后执行，执行完后重新评估。

### 3.3 异常处理

#### 3.3.1 持有者崩溃

- 执行权状态文件包含**时间戳**
- 如果持有者超过 **5 分钟**未更新心跳（时间戳未变化），执行权被视为**过期/作废**
- 等待队列中的下一个实例可以直接接管执行权
- 心跳更新频率：每次执行完一个任务后更新（复用任务完成的时间点自然刷新）

#### 3.3.2 等待者退出

- 如果等待中的实例被手动停止（`stop()`），从等待队列中移除
- 如果等待中的实例的 `pending_task` 变为空（用户手动修改了配置，取消了任务），主动退出等待队列

#### 3.3.3 配置热更新

- 用户在等待期间修改了排队配置（关闭了 `queue_mode`），实例应立即退出排队，恢复正常独立执行模式
- 用户在任务执行期间关闭了 `queue_mode`，实例在完成当前任务后释放执行权，恢复正常模式

### 3.4 不影响的范围

- 未勾选 `queue_mode` 的实例**完全不受影响**，独立并行执行
- 即使所有实例都未勾选，系统行为与现有完全一致（向后兼容）
- Restart 任务作为普通任务参与排队

### 3.5 用户故事

1. **作为多开用户**，我希望多个模拟器在服务器刷新时间点（09:00）能排队依次执行日常任务，而不是同时争抢资源，这样每个账号的任务成功率更高。

2. **作为低配服务器用户**，我希望通过排队模式避免 CPU/内存峰值，让服务器稳定运行。

3. **作为配置者**，我希望排队功能是可选的（opt-in），不影响不需要排队的实例。

## 4. 非功能需求

- **可靠性**：实例崩溃不应导致排队系统死锁
- **性能**：排队检查的轮询间隔为 5 秒，不应显著增加 CPU 开销
- **兼容性**：同时兼容 server 模式、GUI 模式和单机模式
- **可观测性**：排队状态应能通过日志查看，方便调试
